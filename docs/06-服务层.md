# 服务层

## 架构设计

服务层采用 **接口 + 实现分离** 模式。每个 Service 模块定义 `I*Service` 接口，通过 `set*Service()` 注入实现（开发环境注入 Mock，生产环境注入真实 API），统一导出 `*Service` 代理对象。

```
组件/Composables → *Service (代理) → get*Service() → 实现 (Mock/API)
```

### 3.1.1 实时数据订阅契约（docs/19 I1，可选）

传输层由宿主实现（轮询/SSE/WebSocket 均可），引擎只负责合并。宿主实现
`IRecordService.subscribeRecords(moduleId, cb)` 可选成员,回调 `RecordsChangePayload`：

```ts
{
  moduleId: string
  upserts?: RecordEntity[]   // 变更行完整记录(upsert 语义:按 id 合并)
  deletes?: string[]         // 被删除记录 id
}
```

**引擎合并语义**：模块加载完成后自动订阅、卸载退订;upserts 存在则整体替换
（fields/version/updatedAt 静默合并,同步 currentRecord）、不存在则追加（total +1）;
deletes 按 id 移除;**正在行内编辑的行跳过合并并提示冲突**（编辑会话基于旧数据,
结束后由宿主下一次推送自然补齐）。

mock 提供 `createMockRecordSubscription({ intervalMs })` 轮询示例实现（存储快照 diff）,
用法：`setRecordService(Object.assign(new MockRecordService(), createMockRecordSubscription()))`。

### 3.1 标准数据操作契约（宿主执行）

> 定位约定（2026-09-15，docs/19 批次 B3 决策）：**schemagine 专注前端领域的渲染与演算**——
> 引擎负责「渲染操作入口 + 交互确认 + 发出标准化事件」，**不执行任何数据写操作**（不内建
> delete/update）；数据写操作由宿主执行。因此 `IRecordService` 只含读与字段级 patch，
> 这是刻意设计而非缺失。

引擎侧（渲染 + 确认 + 事件）：

| 操作 | 启用条件 | 引擎行为 | 上抛事件 |
|------|---------|---------|---------|
| 行级删除 | `operations.delete.enabled` × `permissions.delete` | 渲染操作列删除按钮 → 二次确认 | `row-action`（`actionId: 'delete'`） |
| 批量删除 | `operations.delete.batch`（且 enabled） | 收集勾选行 → 二次确认 | `action-trigger`（`action.type: 'delete'`，`context.selectedRowIds`） |
| 单字段更新 | 行内编辑（受权限/条件约束） | 编辑控件 + 精度校验 + 乐观锁重试 | 引擎经 `patchField` 直接提交（读改写属于演算环节） |
| 批量字段更新（宿主模式） | `operations.batchPatch.enabled`（docs/19 H4） | 批量编辑对话框收集 + 校验 → 原子语义上抛 | `batch-patch`（`BatchPatchEvent`：`moduleId + ids + patch`） |
| 批量字段更新（缺省引擎路径） | 未配置 `batchPatch.enabled` | 引擎本地逐条 `patchField`；**存在失败时对已成功行补偿回写**（以提交成功返回的版本作 expectedVersion 写回原值），提示按整体口径（"已整体回滚"）而非部分成功 | 不上抛（引擎闭环） |
| 自定义动作 | `listActions` / `rowAction` | 渲染按钮 + `visibleWhen` 显隐 | `action-trigger` / `row-action` 原样上抛 |

宿主侧（执行）：

```ts
<SchemaEngine
  @row-action="async ({ rowId, actionId }) => {
    if (actionId === 'delete') {
      await myApi.deleteRecord(rowId)      // 宿主自己的后端
      engineRef.value?.refresh()           // 完成后刷新引擎数据
    }
  }"
  @action-trigger="async ({ action, context }) => {
    if (action.type === 'delete') {
      await myApi.batchDelete(context.selectedRowIds)
      engineRef.value?.refresh()
    }
  }"
  @batch-patch="async ({ moduleId, ids, patch }) => {
    // 原子语义(docs/19 H4):补丁对 ids 要么全部生效、要么全部不生效——
    // 任一记录失败由宿主在自己的后端整体回滚
    await myApi.batchPatchFields(moduleId, ids, patch)
    engineRef.value?.refresh()             // 完成后刷新引擎数据
  }"
/>
```

契约类型：`RowActionEvent` / `ActionTriggerEvent` / `BatchPatchEvent`（`src/types/events.ts`，经公开 API 导出）；
删除文案与确认弹窗配置见 `ModuleSchema.operations.delete`（`DeleteOperationConfig`），
批量更新契约开关见 `ModuleSchema.operations.batchPatch`（`BatchPatchOperationConfig`）。

> **batch-patch 契约边界**（docs/19 H4）：宿主模式下引擎不做本地乐观更新、不写入撤销栈
> （数据真源在宿主侧，执行完成以 `refresh()` 重新拉取为准）；缺省引擎路径的批量编辑
> 仍入撤销栈（`useRecordHistory.pushBatchEdit`，docs/05 §8）可整批撤销。

## Mock evaluateFilter 逻辑

Mock 层实现了完整的 `FilterClause` 解析：

```typescript
function evaluateFilter(clause: FilterClause, fieldValue: unknown): boolean {
  if (fieldValue == null) {
    return ['neq', 'notLike', 'notIn', 'notBetween', 'isNotNull'].includes(operator)
  }
  switch (operator) {
    case 'eq': return fieldValue === value
    case 'neq': return fieldValue !== value
    case 'like': return String(fieldValue).toLowerCase().includes(String(value).toLowerCase())
    case 'notLike': return !String(fieldValue).toLowerCase().includes(String(value).toLowerCase())
    case 'in': return values!.some(v => fieldValue === v)
    case 'notIn': return !values!.some(v => fieldValue === v)
    case 'between': return fieldValue >= values![0] && fieldValue <= values![1]
    case 'notBetween': return fieldValue < values![0] || fieldValue > values![1]
    case 'isNull': return fieldValue == null
    case 'isNotNull': return fieldValue != null
  }
}
```

多条件组合（docs/19 批次 E2）：顶层隐式 AND；OR/嵌套用 `FilterGroup`（`{ type: 'group', logic: 'and' | 'or', conditions: FilterCondition[] }`，可递归嵌套）表达。契约类型 `ListQueryParams.filters: FilterCondition[]`（`FilterCondition = FilterClause | FilterGroup`），mock 与本地数据源共用 `utils/filterConditions.ts` 的 `evaluateConditions` 同口径求值：

```typescript
// utils/filterConditions.ts（mock 与 createLocalRecordService 共用）
function evaluateConditions(conditions: FilterCondition[], record): boolean {
  return conditions.every(c => evaluateCondition(c, record))
}
function evaluateCondition(c: FilterCondition, record): boolean {
  if (isFilterGroup(c)) {
    return c.logic === 'or'
      ? c.conditions.some(x => evaluateCondition(x, record))
      : c.conditions.every(x => evaluateCondition(x, record))
  }
  return evaluateFilter(c, record[c.field])
}
```

> 注意：`type: 'group'` 是组的判别字段（FilterClause 无 type），JSON 契约中据此区分叶子与分支。

### 保存视图（FilterPreset，docs/19 批次 E3）

`UserViewConfig.filterPresets: FilterPreset[]` 落地，`FilterPreset = { id, name, filters: FilterCondition[], sort?, isDefault? }`：

- 引擎工具栏支持命名保存当前「筛选 + 排序」、切换、删除、设为默认（`isDefault` 唯一，设为默认时互斥）；
- 默认视图在进入模块时由 ListView 自动应用（宿主 `externalFilters` 优先）；
- 变更经 `presets-change` 事件由 SchemaEngine 持久化到 `UserViewConfig`（先更新内存态再异步落库，失败不打断当前会话）。
