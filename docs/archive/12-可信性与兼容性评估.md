# 生产环境可信性与向后兼容评估

> 评估基准：投入生产后，Schema 升级能否平滑过渡？已存储的用户数据/配置是否会因引擎升级而损坏或丢失？

---

## 一、核心发现：Schema 版本号存在但未被使用

### 现状

```typescript
// sampleSchemas.ts — 每个模块 Schema 都有 version 字段
export const voucherSchema: ModuleSchema = {
  id: 'module-voucher',
  version: '1.0.0',  // ← 声明了版本号
  // ...
}

// mockStorage.ts — localStorage 也有版本号
const STORAGE_VERSION = 1
```

两个版本号都**仅声明未使用**：无迁移逻辑、无兼容检测、无降级路径。Schema 版本号从未被代码读取和比较。

**这意味着**：修改 Schema 中任何一个字段的 key/type/options → 所有已存储的记录、视图配置、筛选预设、公式表达式窗口期都会断裂，无法平滑过渡。

---

## 二、13 个具体断裂面（逐项审计）

### 🔴 2.1 字段重命名（key 变更）

**现状**: `RecordEntity.fields` 是 `Record<string, unknown>`，用 `field.key` 作属性名。记录数据以 key 存取。

**断裂路径**:

```
Schema v1: fields: [{ key: 'vendor', type: 'fk', ... }]
用户数据: { vendor: 'VEN-001' }

Schema v2: fields: [{ key: 'supplier', type: 'fk', ... }]  ← 改名
用户数据: { vendor: 'VEN-001' }  ← 旧 key 的数据变成"幽灵字段"，不渲染不报错
```

**现状表现**: 旧数据静默丢失，用户无感知，列为空。

**评级**: 🔴 数据静默丢失

### 🔴 2.2 字段删除（key 移除）

**现状**: `visibleFields` computed 过滤掉 `visible: false` 的字段后按 `order` 排序。已删除的字段不在新 Schema 中，`RecordEntity.fields` 中对应数据成为孤儿。

**断裂路径**:

```
Schema v1: fields: [{ key: 'remark', type: 'text' }, ...]
用户数据: { remark: '重要备注' }

Schema v2: remark 字段删除
ListView: 不渲染 remark 列（数据在 fields 中但不显示）
UserViewConfig.columns: 可能仍包含 { field: 'remark', visible: true, ... }  ← 幽灵列配置
```

**现状表现**: `ColumnConfig` 中引用不存在的 field key 时，`SchemaTable.columns` computed 中 `configMap.get(field.key)` 返回 undefined，`visible: undefined` 导致列被过滤。**不会崩溃，但旧列配置残留。**

**评级**: 🔴 数据残留 + 配置膨胀

### 🔴 2.3 字段类型变更

**现状**: `FieldEditorFactory.editorComponent` 根据 `field.type` 选择编辑器。

**断裂路径**:

```
Schema v1: { key: 'amount', type: 'text' }
用户数据: { amount: '1000' }           ← 字符串

Schema v2: { key: 'amount', type: 'number' }
字段编辑器: NumberEditor               ← 期望数字
用户数据: { amount: '1000' }           ← 字符串
```

**现状表现**: `ElInputNumber` 接收字符串 `'1000'` → 绑定值变为 `NaN` 或 `0`。**数据语义静默损坏。** 反之（number → text）问题较小但旧数值变为字符串展示。

**评级**: 🔴 数据语义损坏

### 🟡 2.4 公式字段逻辑变更

**现状**: `FormulaFieldConfig` 包含 `expression` 和 `dependencies`。公式变更（如 `amount * taxRate` → `amount * taxRate * 1.13`）后，新记录用新公式、旧记录保留旧结果。`evaluateAllFormulas` 不会对已存在记录重新计算。

**断裂路径**:

```
Schema v1: formula: 'amount * taxRate'
旧记录 taxAmount: 1000 * 0.13 = 130

Schema v2: formula: 'amount * taxRate * 1.13'
旧记录 taxAmount: 130 (旧值，未重算)
新记录 taxAmount: 1000 * 0.13 * 1.13 = 146.9
```

**现状表现**: 新旧共存的数据不一致，用户在同一个列表里看到不同计算标准的结果。

**评级**: 🟡 数据语义不一致

### 🟡 2.5 用户视图配置（UserViewConfig）陈旧

**现状**: `UserViewConfig.columns` 存储用户的列设置。Schema 升级后新增字段默认不展示（因为 viewConfig 中没有），已删除字段的列配置残留（`columns.find(c => c.field === 'deletedKey')` 返回 undefined，列不被渲染但配置数据不清理）。

**断裂路径**:

```
Schema v1: viewConfig.columns = [{ field: 'amount', visible: true, order: 3, ... }]
Schema v2: 新增字段 'taxAmount', 删除字段 'remark'
  → viewConfig 中没有 taxAmount → taxAmount 列不显示
  → viewConfig 中有 remark → remark 列找不到 Schema，不显示但 columns 数组中有垃圾数据
```

**现状表现**: 用户看不到新字段，需要手动进入列设置勾选。旧列配置垃圾数据累积（localStorage 无限膨胀风险低但存在）。

**评级**: 🟡 用户体验断裂 + 配置残留

### 🟡 2.6 外键目标模块变更

**现状**: FK 字段的 `targetModule` 指向候选值模块。如果目标模块 ID 变更，`candidateService.query()` 返回空。

**断裂路径**:

```
Schema v1: { key: 'vendor', type: 'fk', targetModule: 'module-vendor' }
Schema v2: { key: 'vendor', type: 'fk', targetModule: 'module-supplier' }
  → 旧记录的 vendor: 'VEN-001' 在新 targetModule 中不存在 → 显示为 FK ID 而非 label
```

**评级**: 🟡 FK 显示断裂

### 🟡 2.7 下拉选项变更

**现状**: `select/multi-select` 字段的 `options` 包含 `{ label, value }` 对。`ValueRenderer` 用 `options.find(o => o.value === val)` 来显示 label。

**断裂路径**:

```
Schema v1: status options: [{ label: '草稿', value: 'draft' }, { label: '已审核', value: 'approved' }]
Schema v2: status options: [{ label: '草稿', value: 'draft' }]  ← 删除 'approved'
  → 旧记录 status='approved' → ValueRenderer 找不到 label → 显示原始值 'approved'
```

**现状表现**: `ValueRenderer.formatValue` 找不到 label 时 fallback 到 `String(value)`。**不会崩溃，但 UI 降级为显示原始 key。**

**评级**: 🟡 UI 降级（可接受但需改进）

### 🟡 2.8 聚合字段变更

**现状**: `FieldSchema.aggregation` 从 `'sum'` 改为 `undefined` → `useAggregation` 不再计算该字段。从 `undefined` 改为 `'sum'` → 旧记录的该字段如果存储了非数字值，`Number()` 会得到 `NaN` 并被过滤，不影响整体但丢失该行贡献。

**评级**: 🟡 无感变更（可接受）

### 🔴 2.9 数据格式版本不一致

**现状**: `mockStorage.ts` 使用 `STORAGE_VERSION = 1` 来标记整个 localStorage 命名空间的版本。如果存储数据格式变更（如 `DraftRecord.fields` 结构变化、`UserViewConfig` 结构变化），旧格式数据与新代码不兼容。

**断裂路径**:

```
STORAGE_VERSION = 1 时存储的 UserViewConfig 格式:
{ moduleId, version, columns, pageSize }

STORAGE_VERSION = 2 时新增字段 cardLayout:
代码读取旧数据后 cardLayout 为 undefined，代码后续使用 cardLayout?.fields 时可能出错
```

**现状表现**: `isStorageInitialized()` 检查 `meta.version === STORAGE_VERSION`，版本不匹配时 `seedRecordsIfNeeded` 不会执行（但也不会清理旧数据）。**如果 STORAGE_VERSION 提升，旧数据全部变孤儿。**

**评级**: 🔴 数据格式断层

### 🔴 2.10 乐观锁版本不匹配时的降级路径

**现状**: `patchField` 使用 `expectedVersion` 进行乐观锁校验。版本冲突时返回 `VERSION_CONFLICT`，`useCellEdit.handleSaveError` 弹出确认对话框。

**断裂路径**: 生产环境多用户并发编辑 → 版本冲突频率远高于 Mock 环境 → 用户频繁看到冲突对话框 → 无自动合并/刷新机制。

**评级**: 🔴 无自动恢复路径

### 🟡 2.11 错误边界缺失

**现状**: 搜索整个 src 目录，无 `errorCaptured` / `onErrorCaptured` / ErrorBoundary 组件。引擎内部任何一个子组件抛出未捕获异常，整个 `SchemaEngine` 崩溃为白屏。

**断裂路径**:

```
公式引擎 safeeval 抛出未被 try/catch 覆盖的异常
  → Vue 渲染函数崩溃
    → 整个 SchemaEngine 卸载
      → 用户看到白屏 + 控制台错误栈
```

**现状表现**: `useFormula.safeEval` 有 try/catch，`useSchema.loadModule` 有 try/catch，`ListView.fetchData` 有 try/catch。**但组件渲染层（模板表达式、computed 属性）无保护。**

**评级**: 🟡 缺少容错层

### 🟡 2.12 服务层注入失败保护

**现状**: Service 代理调用 `get*Service()`，未初始化时抛出 `Error`。`main.ts` 中 `initMockServices()` 在 `createApp` 之前执行。但如果开发者在 `createApp` 之后动态添加模块而未重新注入，访问会抛异常。

**评级**: 🟡 缺少防御性降级

### 🔴 2.13 内存泄漏风险

**现状**: `VxeTableWrapper.vue` 中有 `ResizeObserver`，但代码中未见 `onUnmounted` 中的 `disconnect()` 调用。模块切换时 Observer 可能残留。

**评级**: 🔴 长期运行风险

## 三、Schema 平滑升级的 8 条必要能力（现状全缺）

| # | 能力 | 现状 | 投产阻塞 |
|---|------|------|----------|
| 1 | Schema 版本号比对 | `ModuleSchema.version` 声明但未读取 | 🔴 是 |
| 2 | 字段重命名声明 | 无 `previousKeys` / `aliases` | 🔴 是 |
| 3 | 字段删除声明 | 无 `deprecated` / `removedAt` | 🔴 是 |
| 4 | 数据迁移函数 | 无 `migrateRecord(fromVersion, toVersion, record)` | 🔴 是 |
| 5 | 用户配置合并 | 无 viewConfig.columns 与 schema.fields 的 diff/merge | 🔴 是 |
| 6 | 公式漂移检测 | 无旧记录与当前公式的结果对比 | 🟡 否 |
| 7 | 灰度开关 | 无 `featureFlags` / 新旧公式双跑 | 🟡 否 |
| 8 | 数据格式版本迁移 | `STORAGE_VERSION` 变更时无数据迁移 | 🔴 是 |

## 四、投产前最低安全门禁（P0 必须）

### 4.1 Schema 兼容性声明协议

新增 Schema 字段描述向后兼容策略：

```typescript
// 建议新增的字段
interface FieldSchema {
  // ... 现有字段

  /** @since 2.1.0 字段重命名：旧 key 列表，引擎自动映射 */
  previousKeys?: string[]

  /** @since 2.1.0 字段弃用：从此版本开始废弃 */
  deprecatedSince?: string

  /** @since 2.1.0 字段移除：从此版本开始移除（数据归档） */
  removedAt?: string
}

interface ModuleSchema {
  // ... 现有字段

  /** @since 2.1.0 迁移列表：按版本号排列的迁移函数 */
  migrations?: SchemaMigration[]
}

interface SchemaMigration {
  fromVersion: string
  toVersion: string
  /** 迁移单条记录 */
  migrateRecord: (record: Record<string, unknown>) => Record<string, unknown>
  /** 迁移用户配置 */
  migrateViewConfig?: (config: UserViewConfig) => UserViewConfig
  /** 迁移筛选预设 */
  migrateFilterPresets?: (presets: FilterPreset[]) => FilterPreset[]
}
```

### 4.2 Schema 加载时的兼容处理流程

```
loadModuleSchema(moduleId)
  ├─ 1. 获取 Schema v2
  ├─ 2. 获取该模块的 storedRecords（旧字段 key）
  ├─ 3. 执行 migrations[]:
  │    ├─ previousKeys 映射: { oldKey → newKey }
  │    │   例: record.fields[newKey] = record.fields[oldKey]; delete record.fields[oldKey]
  │    ├─ migrateRecord: 自定义转换（如 text→number: Number(oldValue)）
  │    └─ migrateViewConfig: columns 中更新 field key
  ├─ 4. 验证迁移后数据完整性
  └─ 5. 写回存储 + 返回
```

### 4.3 最小破坏性变更清单（新增字段类型安全）

```typescript
// 在 useSchema.loadModule 内部新增逻辑
function ensureViewConfigCompatibility(
  schema: ModuleSchema,
  viewConfig: UserViewConfig,
): UserViewConfig {
  const validKeys = new Set(schema.fields.map(f => f.key))

  // 1. 清理已删除字段的列配置
  const cleanColumns = viewConfig.columns.filter(c => validKeys.has(c.field))

  // 2. 补充新增字段的默认列配置
  const existingKeys = new Set(cleanColumns.map(c => c.field))
  const maxOrder = cleanColumns.length > 0
    ? Math.max(...cleanColumns.map(c => c.order))
    : -1
  for (const field of schema.fields) {
    if (!existingKeys.has(field.key)) {
      cleanColumns.push({
        field: field.key,
        width: field.width || 120,
        visible: true,        // ← 新字段默认可见
        order: maxOrder + 1,
        sortable: !!field.sortable,
      })
    }
  }

  return { ...viewConfig, columns: cleanColumns }
}
```

### 4.6 乐观锁自动恢复

```typescript
// 版本冲突时自动刷新记录后重试编辑
async function onCellEditWithRetry(payload, maxRetries = 1): Promise<void> {
  for (let i = 0; i <= maxRetries; i++) {
    const res = await recordService.patchField(payload)
    if (res.success) return
    if (res.errorCode === 'VERSION_CONFLICT' && i < maxRetries) {
      // 自动刷新该记录后重试
      await recordService.getDetail(moduleId, payload.rowId)
      continue
    }
    throw res
  }
}
```

## 六、投产建议优先级

| 优先级 | 工作 | 估时 | 影响范围 |
|--------|------|------|----------|
| 🔴 P0-1 | Schema 版本比对 + `previousKeys` 字段重命名映射 | 2d | 数据不丢失 |
| 🔴 P0-2 | `ensureViewConfigCompatibility` 列配置自动合并 | 1d | 用户体验不断裂 |
| 🔴 P0-3 | ErrorBoundary 错误边界组件 | 0.5d | 避免白屏崩溃 |
| 🔴 P0-4 | `STORAGE_VERSION` 数据格式迁移框架 | 1d | 存储格式升级不丢数据 |
| 🔴 P0-5 | `onUnmounted` 清理（ResizeObserver 等） | 0.5d | 长期稳定运行 |
| 🟡 P1-1 | 字段类型变更时的数据转换（`migrateRecord`） | 2d | 类型安全过渡 |
| 🟡 P1-2 | 乐观锁自动刷新重试 | 1d | 并发编辑体验 |
| 🟡 P1-3 | 公式重算检测与提示 | 1d | 公式变更数据一致性 |
| 🟡 P1-4 | 服务注入降级实现 | 0.5d | 防御性编程 |
| 🟡 P1-5 | Store 输入校验 | 1d | 数据防污染 |

> **总结**：当前引擎在 Demo 环境运行良好，但投入生产必须在 Schema/Dual 版本兼容层面补齐 5 项 P0 能力，否则任何一次 Schema 字段调整都会造成静默数据丢失或用户配置断裂。Schema 版本号已有声明基础，补齐迁移框架不涉及架构重构。
