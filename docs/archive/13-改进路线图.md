## Phase 1：生产容错基础（估时 2.5d）

> 目标：引擎崩溃不白屏、长期运行不泄漏、服务未就绪不抛异常。

### 任务 1.1 — ErrorBoundary 错误边界

| 项 | 内容 |
|----|------|
| **目标** | 子组件渲染异常 → 隔离降级，不影响整个引擎 |
| **涉及文件** | 新建 `src/engine/providers/ErrorBoundary.vue`；修改 `SchemaEngine.vue` 包裹子组件 |
| **实现要点** | 使用 Vue3 `onErrorCaptured` 捕获子组件异常；展示内联错误卡片（含错误消息 + 重试按钮）；不吞没公式/编辑等逻辑层异常（仅捕获渲染层） |
| **验收标准** | ① 在子组件 `onMounted` 中 `throw new Error('test')` → 引擎不白屏，显示错误卡片 + 重试按钮 ② 点击重试按钮 → 重新挂载子组件 ③ 公式计算异常不受影响（仍走现有 try/catch） |
| **估时** | 0.5d |

### 任务 1.2 — 内存泄漏清理

| 项 | 内容 |
|----|------|
| **目标** | `ResizeObserver`、事件监听器在组件卸载时释放 |
| **涉及文件** | `VxeTableWrapper.vue`、`SchemaFilterBar.vue` 及其他使用 observer/listener 的组件 |
| **实现要点** | `onUnmounted` 中调用 `resizeObserver.disconnect()`；全局搜索 `addEventListener` / `new ResizeObserver` / `setInterval`，逐一补充 `onUnmounted` 清理 |
| **验收标准** | ① 在 Chrome DevTools Performance Monitor 中，模块切换 50 次后 JS heap size 无持续增长 ② `resizeObserver` 在 `onUnmounted` 中有对应的 `disconnect()` ③ 无 console warning "[Violation] observer took..." |
| **估时** | 0.5d |

### 任务 1.3 — 服务注入降级

| 项 | 内容 |
|----|------|
| **目标** | Service 未初始化时不抛异常，返回降级空实现 |
| **涉及文件** | `services/api/base.ts`（新增 `withFallback` 工厂函数）；`recordService.ts`、`schemaService.ts`、`candidateService.ts`、`userViewConfigService.ts`、`relationService.ts` |
| **实现要点** | 每个 `get*Service()` 增加 `console.error` 警告 + 返回 fallback 实现（recordService fallback 返回空列表，schemaService fallback 返回 NOT_FOUND，candidateService fallback 返回空选项）；`main.ts` 启动时显式检查所有 Service 是否已注入 |
| **验收标准** | ① 不调用 `initMockServices()` 直接 mount → 显示"服务未就绪"提示，不抛 `Error` ② 控制台有对应 warning ③ 不干扰正常流程 |
| **估时** | 0.5d |

### 任务 1.4 — onUnmounted 竞态保护

| 项 | 内容 |
|----|------|
| **目标** | 组件卸载后，pending 的异步回调不更新已销毁组件状态 |
| **涉及文件** | `ListView.vue`、`CardView.vue`、`CreateView.vue` |
| **实现要点** | 每个异步路径在 `await` 后检查组件是否 `isMounted`；可用 `getCurrentInstance()?.isMounted` 或 `useMounted()` composable |
| **验收标准** | ① 快速切换模块 10 次 → 无 "Cannot read properties of null" 错误 ② 无 "Attempting to update unmounted component" Vue warning |
| **估时** | 1d |

## Phase 2：Schema 平滑升级（估时 5d）

> 目标：Schema 任意字段变更后，旧数据自动迁移不丢失、用户配置自动合并不断裂。

### 任务 2.1 — Schema 版本比对 + 字段重命名映射

| 项 | 内容 |
|----|------|
| **目标** | 字段 key 重命名时，引擎自动将旧 key 的数据映射到新 key |
| **涉及文件** | `types/schema.ts`（新增 `FieldSchema.previousKeys`、`ModuleSchema.migrations`）；`composables/useSchema.ts`（`loadModule` 中增加迁移步骤）；`services/mock/mockAdapter.ts`（MockRecordService 加载时执行迁移） |
| **实现要点** | `FieldSchema` 新增可选字段 `previousKeys?: string[]`；`loadModule` 中：加载 Schema → 遍历 `fields` 的 `previousKeys` → 对 `storedRecords` 执行 `record.fields[newKey] = record.fields[oldKey]` + `delete record.fields[oldKey]` → 写回存储 |
| **验收标准** | ① 现有 test: 修改 `voucherSchema` 中将 `remark` 的 key 改为 `summary`，设置 `previousKeys: ['remark']` → 旧记录 `{ remark: 'test' }` 自动变为 `{ summary: 'test' }` ② 未设置 `previousKeys` 的字段不受影响 ③ type-check 0 错误 |
| **估时** | 1.5d |

### 任务 2.2 — SchemaMigration 协议 + 链式迁移

| 项 | 内容 |
|----|------|
| **目标** | 支持多版本间的链式迁移（1.0 → 1.1 → 1.2），任意旧格式数据走到最新格式 |
| **涉及文件** | `types/schema.ts`（新增 `SchemaMigration` 接口）；`composables/useSchema.ts`（新增 `runMigrations` 函数）；`services/mock/mockAdapter.ts`；`__tests__/schemaMigration.spec.ts` |
| **实现要点** | `SchemaMigration` 接口：`{ fromVersion, toVersion, migrateRecord, migrateViewConfig?, migrateFilterPresets? }`；`runMigrations(schema, storedRecords, storedConfig)` 根据 `STORAGE_VERSION` 和 Schema.version 差值链式执行 migration 数组 → 迁移完成更新 `STORAGE_VERSION` |
| **验收标准** | ① 单元测试覆盖：v1 record → v2 migration → v3 migration → 最终数据格式正确 ② 迁移中断（某步抛异常）→ 回滚到迁移前状态，日志记录失败 ③ `STORAGE_VERSION` 随迁移完成递增 |
| **估时** | 2d |

### 任务 2.3 — viewConfig 自动合并

| 项 | 内容 |
|----|------|
| **目标** | Schema 字段增删后，用户列配置自动清理幽灵列 + 补充新列 |
| **涉及文件** | `composables/useSchema.ts`（新增 `ensureViewConfigCompatibility` 函数，在 `loadModule` 中调用） |
| **实现要点** | ① `validKeys = new Set(schema.fields.map(f => f.key))` ② `cleanColumns = viewConfig.columns.filter(c => validKeys.has(c.field))` ③ 新字段追加 `{ field: f.key, width: f.width||120, visible: true, order: maxOrder+1, sortable: !!f.sortable }` ④ 写回 `schemaMeta.setViewConfig(merged) + userViewConfigService.save(merged)` |
| **验收标准** | ① 在 `voucherSchema` 中新增 `newField` → 打开模块后列设置弹窗中自动包含 `newField`，默认勾选 ② 删除 `remark` 字段 → viewConfig 中的 remark 列自动移除 ③ type-check 0 错误 |
| **估时** | 1d |

### 任务 2.4 — 乐观锁自动刷新重试

| 项 | 内容 |
|----|------|
| **目标** | 版本冲突时自动刷新记录后重试编辑，减少用户手动操作 |
| **涉及文件** | `composables/useCellEdit.ts` |
| **实现要点** | `onCellEdit` 中 `patchField` 返回 `VERSION_CONFLICT` → 自动调用 `recordService.getDetail()` 刷新记录 → 用最新 `version` 重试一次 → 二次失败再弹冲突对话框 |
| **验收标准** | ① 模拟版本冲突 → 自动重试 1 次成功 → 无冲突弹窗 ② 连续 2 次冲突 → 弹出版本冲突对话框 ③ `source: 'formula'` 的编辑不重试（公式编辑不触发乐观锁） |
| **估时** | 0.5d |

## Phase 3：多实例隔离 + npm 可分发（估时 3d）

> 目标：同一页面嵌入两个 SchemaEngine 不冲突；npm publish 后可 `import { SchemaEngine } from 'schemagine'`。

### 任务 3.1 — loadingModuleId 实例作用域化

| 项 | 内容 |
|----|------|
| **目标** | 两个 SchemaEngine 实例各自独立加载模块，不互相干扰 |
| **涉及文件** | `composables/useSchema.ts`、`engine/entry/SchemaEngine.vue` |
| **实现要点** | 方案 A（推荐）：`loadingModuleId` 从模块级 ref 移入 `useSchema()` 函数作用域内（每次调用 `useSchema()` 创建独立实例）。方案 B：通过 `provide/inject` 按实例 ID 隔离。需同步检查 `useRecordStore` 等是否也需按实例隔离（Store 天然多例 — Pinia 允许 `defineStore` 多次 use） |
| **验收标准** | ① 同一页面渲染 2 个 `<SchemaEngine moduleId="module-voucher" />` → 各自独立加载、独立渲染、不报错 ② 快速切换两个实例的模块 → 无竞态错误 ③ 现有单实例场景不退化 |
| **估时** | 1.5d |

### 任务 3.2 — npm 包 Library Mode 构建

| **目标** | 所有中文文案 key 化，支持中/英文切换 |
